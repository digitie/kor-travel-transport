# 경의중앙선 복합 식별 비교키의 표기 차이

## 문제와 변경 범위

3691 운영의 도시철도 서울역823은 `unlinked`였다. 저장 기준정보는
`코레일|경의중앙선|1251|서울역`, 공식 코드 catalog의 해당 후보는
`KR/K4/P313`, 표시명은 `한국철도공사/경의중앙/서울역`이었다.
기존 비교키가 기관·노선명을 그대로 비교해 결과가 비는 것을 순수 fixture로 먼저 재현했다.

자동 연결은 [Transport 매핑 도메인](../../backend/app/services/rail_station_mapping.py)의 책임이다.
provider parser나 adapter를 추가하지 않고, 기존 `exact_identity` 비교키만 다음과 같이 바꾼다.

- 기준정보의 `코레일/경의중앙선`, `한국철도공사/경의중앙`을 같은 비교 범위로 취급한다.
- 공식 코드 쪽에서는 **운영기관 KR·노선 K4**이고 위 두 표기 중 하나인 경우에만 그 범위를 쓴다.
  이름 공간을 구분해 다른 운영기관·노선이 같은 표시명을 가져도 이 별칭으로 연결하지 않는다.
- 역명은 원문에서 앞뒤 공백만 제거해 비교한다. 정규화한 복합 tuple의 code 쪽 건수와
  기준정보 쪽 후보 수가 **각각1**이어야 한다. 이름만 같은 후보를 연결하지 않는다.
- `1251`→`P313` 같은 번호 변환이나 역별 예외는 없다. 원문 이름·번호·identity·raw·catalog는 유지한다.
  별칭으로 합쳐진 복합 tuple이 모호하면 번호 분기로 우회 확정하지 않는다. 이 범위 밖의 기존
  번호+정규역명 분기, exact 대상 재사용 거절, 수동 연결 우선과 target 단일 점유는 그대로다.

다른 공식 code tuple에는 이 복합키 별칭이 적용되지 않는다. 기존의 별도 번호+정규역명 전략을
전국적으로 없애거나 확대하는 변경도 아니다.

## 근거를 분리해서 해석하기

1. [코레일 공식 보도자료](https://info.korail.com/info/selectBbsNttView.do?bbsNo=199&key=911&nttNo=7670)는
   한국철도와 코레일의 병기, 경의중앙선이라는 광역철도 노선 표기를 제공한다.
   이는 기관·노선의 표시명 근거이며 **1251↔P313 직접 대응 행은 아니다**.
   직접 페이지 열기는 도구에서 실패했고 같은 공식 게시물의 검색 색인 내용으로 표기를 대조했다.
2. 2026-10-27 기존 관리자 매핑 GET의 저장 DTO에는 위 공식 code tuple/표시명과 기준정보의 원문이
   함께 있었다. catalog SHA256은
   `f41f17e3c523df083eaa96a835daff9a4f3666037d5d29753c9a44a3c56b319b`,
   catalog 갱신은 `2026-10-25T06:01:58.881481Z`다.
   SDK의 공식 역사 코드 파일 파서가 보존하는 `RAIL_OPR_ISTT_CD/LN_CD/STIN_CD`와
   공개 역사정보 dataset1294의 표시 기관·운영노선·역 번호는 서로 다른 필드다.
3. 별도 읽기 진단의823 저장 raw에는29개 키가 있고 `FR_CODE/STATION_CD` 대응 열은 없었다.
   번호로 확인된 값은1251뿐이다. 따라서 직접 code crosswalk를 확보했다는 주장은 하지 않는다.

이 수정은 공식 code 범위와 양쪽 저장 catalog의 유일한 복합 이름을 이용하는 기존 전략을
표기 차이에 적용한 것이다. 실제 운영의 모든 역이나 모든 노선에 대한 동일성 증명은 아니다.
공식 code crosswalk를 외부에 제공하려면 별도 공식 대응 행이 필요하다.

## 회귀와 검증

[매핑 테스트](../../backend/tests/test_rail_station_mapping.py)는 관측된 두 원문의 RED 재현 뒤
정상 복합키 연결, 타기관·타노선6조합, 정규화 뒤 양쪽 중복과 순서 반전, 역명만 일치하는 후보 거절,
원문·번호 보존, 기존 공항철도 번호 분기 및 수동 target 점유 보호를 확인한다.

- WSL2 RED: 기존 코드에서 관측 fixture **1실패**. 연결 결과 `[]`를 확인했다.
- WSL2 1차: 매핑·관리 API·수집·철도 export 인접4파일 **62통과·1건너뜀**.
  이후 타기관·타노선 원문 표기 음성3사례를 더해 최종 매핑 파일 **22통과**를 확인했다.
- Docker2차 인접4파일 **65통과·1건너뜀**. 최종 음성3사례를 포함하며 기존 이미지의
  의존성을 재사용하고 현재 작업트리를 읽기 전용 mount했다. 이 집중 검증은 network=none으로
  provider·운영망을 사용하지 않았고 owned 임시 컨테이너는 자연 종료했다.
- 첫 후보 `0e4881b`의 추가 경계 검토에서 별칭 모호성이 기존 번호 fallback으로 우회되는
  좌·우 각1사례를 **RED 2실패**로 재현했다. 별칭 namespace에만 우회 거절을 추가하고,
  일반 복합키의 기존 번호 fallback 보존까지 더한 최종 매핑 파일은 **25통과**다.
  앞선62/65 수치는 이 추가 보호 전 후보의 결과이며 최종 전체 검증을 대신하지 않는다.
- 소스 동결 뒤 WSL/Docker 전체 backend, 정확 head의 전체 CI·두 독립 적대 리뷰는
  별도 확인 후 기록한다.
  WSL1차를 전체 CI나 운영 수용으로 대신하지 않는다.

SDK `5bf0e616` 고정, 의존성·schema·공개 DTO·job·수집 코드는 바꾸지 않는다.
이 고정 SDK의 시설 tuple/긍정값 파서와 이를 쓰는 features API도 이미 있으며 이번 변경 대상이 아니다.

## 운영 수용과 남은 범위

제품 후보를 운영에 적용하거나, 관리 POST·기존14개 manual 배열 수정·DB/provider 조회·수집 실행·
job·운영 빌드·배포를 하지 않았다. 이번 개발에서 운영·DB·provider 추가 요청은0이다.

새 코드로 계산한 **effective 연결**은 실제 저장 FK와 같은 개념이 아니다. 기존 registry에 저장된
automatic 배열을 소비하는 경로도 있어 코드 교체만으로 기존 배열이 반드시 재계산되는 것은 아니다.
기존 정규 참조 수집 경로의 FK/registry 반영과, 해당 역·요일의 저장 시간표 snapshot·신선도·실제 UI의
이후 출발편을 별도로 검증해야 한다. 이번 fixture 통과로 시간표 복구나 T-RAIL-03 완료를 선언하지 않는다.
