# 실제 2146 배포 뒤 장소·참조 읽기 중복 비용

기준은 main 2146d8ef6023c2f59fd34e9c6f1f24b8663fcc23이다.
부모가 전달한 실제 SDK 적용·UI 3단계 성공과 읽기 성능 수용은 구분한다.
운영 places는 같은 데이터의 3표본에서 8.27/4.56/6.96초, SQL 6개·3.32~4.97초였다.
rail stations warm304의 5표본 p95는 410.85ms였다. 1초·300ms 목표는 여전히 미수용이다.

## 확인한 중복과 수정

place_queries()의 돌발 조회는 24시간 이력에서 source/identity별 최신 ID를 고른다.
COUNT와 제한 페이지가 같은 window를 각각 실행했다. 운영 읽기 전용 EXPLAIN도 중복 구조를
보였으며 추정 비용은 5,257.21·JIT 항목 없음이었다. 전체 UNION의 ANALYZE는 6초 상한에서
취소돼 실제 JIT 시간은 관측하지 못했다. 별도 작은 분해 조회는 총 2.33초에 끝났으며,
돌발만 문장 650ms 상한에 걸렸다. 다른 6종류의 실행시간은 각각 약 10~90ms였다.
이 관측만으로 운영 지연 전부의 원인이나 JIT·주차 캐시 간섭을 확정하지 않는다.
기존 컨테이너 stdin과 정본 설정을 사용해 READ ONLY·짧은 문장/잠금 상한을 적용했으며,
행 본문·접속값·비밀값 출력과 추가 대형 GET은 없었다.

합성 35.6만 돌발 이력·206개 identity에서는 약 10.3만 최근 행을 두 번 읽고 순위 계산했다.
이 최신 ID 집합만 MATERIALIZED CTE로 한 번 계산해 COUNT와 페이지가 공유한다.
좌표·출처·검색은 최신 행 선택 뒤 적용하므로 최신 관측의 좌표가 없을 때 과거 위치를 되살리지 않는다.
이름·정렬·정확한 총계·종류별 균등 제한·원문 투영 계약을 유지한다.

조건부 참조 조회는 미만료 handle을 조회한 뒤 artifact를 두 번 SELECT했다.
ORM identity map의 약한 참조만으로는 함수가 끝난 뒤 첫 artifact 객체가 보존되지 않았다.
같은 RR에서 handle과 artifact metadata를 함께 읽고 호출자에게 함께 전달한다.
입력 revision·kind/scope·수량/digest·승인 시각·만료 검증은 유지하며 cursor는 기존 경로다.
warm304는 페이지 본문·fingerprint를 읽지 않고 SQL 7→5개가 된다.

## 로컬 관측과 CPU 한계

PostgreSQL18·WSL Python 3.13의 합성 표본이며 실제 운영 데이터 사본이나 ARM 수용이 아니다.
종류별 규모는 운영을 참고했으나 기본 공항 등 표본 수는 다르다. 두 버전의 반환 2,670개와
generated_at 제외 데이터 SHA가 일치했다. 시각 창이 흐르며 최근 이력 수는 조금 달라진다.

| 항목 | 기준 | 수정 |
| --- | ---: | ---: |
| places 3회 중앙값 | 544.8ms | 391.6ms |
| places UNION 중앙값 | 351.8ms | 237.1ms |
| EXPLAIN 전체 실행 | 378.0ms | 197.6ms |
| 프로세스 CPU 중앙값 | 142.7ms | 148.5ms |
| 참조 warm304 5회 중앙값 | 43.3ms | 40.6ms |
| 참조 warm304 SQL | 7 | 5 |

같은 DB·같은 cutoff를 고정한 별도 3회 교대 SQL 비교도 결과 digest가 동일했다.
최신 순위 실제 loop는 2→1회, 이력 읽기는 204,352→102,176행, PostgreSQL 실행은
350.7→193.2ms였다. driver 구간 중앙값은 389.5→225.3ms·그 구간 프로세스 CPU는
14.1→11.4ms였다. 양쪽 실제 ANALYZE의 JIT 항목은 없었다.
이는 SQL 구간 관측이며 전체 HTTP CPU 감소나 운영 목표 달성을 뜻하지 않는다.

places SQL 수는 6개 그대로이며 CPU 개선은 입증하지 못했다.
로컬 전후 ANALYZE에는 JIT 항목이 없었다.
별도 warm 표본은 DTO 검증 CPU 12.4ms·직렬화 10.7ms·SQL driver 구간 CPU 20.1ms였다.
첫 DTO 검증은 117.7ms였고 뒤 표본에서 줄었다. 나머지는 행 조립·요청 처리와 측정 클라이언트의
본문 파싱 등을 포함하므로 전부 DTO 비용으로 귀속하지 않는다. 운영 2.2MB 본문의 CPU·호스트
경합과 응답 목표는 별도 실제 관측이 필요하다. places에 응답 캐시·응답 TTL은 없으며
generated_at을 키로 응답을 캐시하는 구조도 없다.

## 검증·범위

- 최신 좌표 없는 관측의 과거 위치 부활 방지·기존 경로의 전체 DTO 동등성을 검증한다.
- 실제 실행계획에서 돌발 PARTITION window가 한 번 실행되는지 확인한다.
- warm304 SQL 상한 5개·본문/fingerprint 읽기 0회와 손상된 artifact kind의 503을 검증한다.
- 신규 회귀는 기준 2개 실패→수정 2개 통과를 확인했다.
- WSL PostgreSQL 집중 70개(111.56초), Docker 동일 범위 70개(127.49초)가 통과했다.
  OpenAPI는 동일하고 신규 시험 lint·변경 Python의 문법/이름 오류 검사를 통과했다.
  기존 export_references.py의 import 순서·Depends 기본값 스타일 지적은 이 수정과 무관하게 남아 있다.
- 운영 이미지·배포·DB 스키마·수집·캐시 설정·CI 순서 변경은 없다.
  TRN04는 부모의 INCONCLUSIVE / BASELINE_NOT_PROVEN_OUTSIDE_REBUILD 판정을 유지한다.
  memory limit 0을 실제 512MiB 하드 제한으로 기술하지 않는다.
