# KRIC 예정 시간표 저장·조회

## 확인된 제공자 계약

2026-09-27 승인 키 진단에서 역사정보 34행, 불광역 휴일 시간표 344행의 HTTP 200을
확인했다. 실제 JSON은 `header.resultCnt`와 `body` 배열이다. 파싱 수정은
`python-kric-api` PR #7에 둔다. transport에 별도 KRIC 응답 파서를 만들지 않는다.

역사정보는 역 코드를 전달해도 노선 전체를 반환할 수 있다. 행의 운영기관·노선·역 코드로
식별하며 요청한 역이라고 가정하지 않는다. 시간표의 원문 `000030`은 그대로 보존한다.
이 데이터는 실시간 도착이 아니라 제공기관의 예정 시각이다.

## 기준정보 연결

서비스키가 필요 없는 KRIC 자료실 역 코드 파일과 [dataset `1294` 전국 도시광역철도 역사정보](https://data.kric.go.kr/rips/M_01_01/detail.do?id=1294)
위치 파일은 별도 출처다. 코드 파일은 KRIC의 `운영기관, 노선, 역 코드정보 리스트(2026.02.28)`
갱신 공지 파일을 사용한다. KRIC가 공개한 위치 파일은 2026-07-01 자료이며 페이지의 수정일은
2026-06-29, 정기 갱신 주기는 별도로 정해져 있지 않다. [KRIC 코드 목록 갱신 공지](https://data.kric.go.kr/rips/M_04_01/detail.do?id=395)는 신규역
추가와 일부 역 코드 변경을 명시하므로 JSON을 영구 고정하지 않고 매핑 화면의 카탈로그 지문과
수동 새로고침·정기 수집으로 변경을 확인한다. 2026-10-20에 내려받은 두 표본은 각각 1,108행이다.
운영기관명·노선명·역명 세 필드의 정확한 유일 일치 500건에 더해, KRIC 역 코드와 위치 파일의
`역 번호`가 같고 NFKC·괄호 부역명·끝의 `역`·공백만 보수적으로 정규화한 역명이 유일하게
일치하는 423건을 연결했다. 총 923건이며, 남은 185건은 이름만으로 추측하지 않고 관리 화면에서
수동 연결한다. 동일 역명만으로 다른 운영기관·노선의 역을 연결하지 않는다. 위치 파일 역 번호는
두 공개 자료를 대조하는 키일 뿐 KRIC 인증 API 요청 코드가 아니다. 코드·이름 전체와 자동·수동
연결 결과는 `kric_station_mapping_registry`의 JSONB에 저장하고, 자료실 원문은 기존대로
RustFS에 checksum과 함께 보관한다. `/rail/mapping`은 로그인 관리자 전용으로 역명·운영기관·
노선·코드 검색, 수동 연결·해제, 전체 JSON 내보내기를 제공한다. 저장 시 catalog revision을
비교해 다른 관리자가 갱신한 뒤의 오래된 화면이 변경을 덮어쓰지 못하게 한다.

자동 매핑은 코드를 고정 정본으로 삼는다. 먼저 운영기관·노선·역명의 정확한 유일 일치를
사용하고, 불일치만 역 코드=위치 파일 역 번호와 정규화 역명으로 대조한다. 양쪽 후보가
유일하고 대상 장소를 중복 점유하지 않을 때만 적용한다. 수동 연결은 별도 JSON에 보존되고
다음 KRIC 파일 수집 뒤에도 같은 역 코드에 재적용한다. 새 코드 목록에 없는 오래된 수동 항목은
효과 연결에서는 제외한다. 공식 제공자와 연결되지 않은 역은 미연결 상태를 유지한다.

## 수집 안전장치

- Dagster가 due 여부를 확인하되 실제 배치는 직전 **시도**에서 최소 48시간 이후에만 시작한다.
  실패·강제 종료 뒤에도 즉시 재시도하지 않는다. 성공 시각만으로 제한하지 않는다.
- PostgreSQL 별도 연결의 advisory lock으로 동시 배치를 막는다. 수집 transaction의
  commit이 lock을 해제하지 않아야 한다.
- 한 배치의 호출 수와 간격을 제한하고 오래된/미수집 역·요일을 먼저 보충한다.
- 평일·토요일·휴일은 각각 `8`·`7`·`9`로 별도 저장한다. 미수집·빈 성공·실패를 구분한다.
- 공개 조회와 지도 이동은 저장 데이터만 읽으며 KRIC 요청을 발생시키지 않는다.
- 기존 스냅샷은 새 응답을 검증한 뒤 교체한다. 실패 시 마지막 정상 저장본을 유지한다.
- 원시 예외 문자열에는 인증 URL이 포함될 수 있으므로 운영 기록에는 예외 유형만 남긴다.
- 매시간 due 여부를 평가하되 인증 배치 간격은 48시간 이상이다. 일 단위 cron의 시작
  시각 흔들림 때문에 실제 간격이 72시간으로 밀리지 않도록 한다.

## 조회와 완료 판정

역·요일의 유일 키와 조회 인덱스를 유지한다. 기준정보 연결률, 시간표 저장률, 가장 오래된
저장 시각을 별도로 보여주며 작업 성공을 전국 수집 완료로 표현하지 않는다.
다음 예정 시각은 공휴일/한국 날짜·자정 경계를 확인한 경우에만 계산한다.
달력 확인 실패나 날짜 의미가 불명확한 시각을 실시간 도착으로 표시하지 않는다.

KASI로 검증한 오늘부터 32일의 운행일 구분을 `rail_service_days`에 저장한다. 조회 API는
이 테이블만 읽으며 KRIC뿐 아니라 공휴일 API도 호출하지 않는다. 확인 실패를 평일로
간주하지 않고 마지막 정상 달력을 보존한다.
월별 총건수와 실제 항목 수가 같아야 하며, 이름·날짜·휴일 여부가 누락되어 소비자 변환이
행을 탈락시키면 불완전한 결과로 처리한다. 운행일 미확정과 실제 미수집은 별도 상태다.

`kric_station_codes`의 운영기관·노선·역 코드, `kric_timetable_snapshots`의 역·요일은
각각 유일 키다. 기본 배치는 5초 간격 최대 500회이며 3시간 이후에는 새 요청을 시작하지 않고 다음 배치에서
보충한다. 전체 1,108역 × 3요일을 한 번에 수집했다고 표시하지 않는다. 초기 수집과
순환 보충 중에는 48시간이 지난 저장본이 존재할 수 있으며 계획 시간표만 제공한다.
마감 전에 시작한 요청은 기존 API timeout 이내에 끝날 수 있다.

`GET /v1/transport/rail/timetables?place_ids=1,2`는 저장 장소 ID 1~5개를 받는다.
`day_code=7|8|9`를 명시하면 해당 유형의 계획 시간표만 반환하고 다음 열차를 추정하지
않는다. 오늘 조회도 달력/시간표가 48시간 이내이고 한국 시각 05~23시인 경우에만
다음 예정 시각을 계산한다. 자정 연장 운행과 실시간 지연은 미지원이다.

현재 이 문서는 구현 계약이다. DB·Dagster·조회·UI·운영 검증의 실제 완료 상태는
`docs/resume.md`와 해당 PR의 검증 기록으로 판단한다.
